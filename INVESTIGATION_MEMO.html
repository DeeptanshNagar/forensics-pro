1. Problem Statement & Hypotheses

1.1 Synthetic Incident Scenario

An office administrator reported that a deployed smart camera uploaded three video clips between 02:14 and 02:31 while the facility was closed and unoccupied. The following morning, the owner discovered that motion detection notifications had been switched to OFF. 1.2 Forensic Question & Boundaries

Forensic Question: Based on the evidence that can be lawfully acquired from the synthetic LumiCam C2 camera, its local network environment, its companion application, and associated cloud service records, what best explains the modification of the motion alert setting to OFF at 02:10 and the three video clip uploads between 02:14 and 02:31 on Day 2, and with what level of certainty?

In Scope: Technical examination of volatile memory on the live camera, non-volatile onboard flash storage, removable storage (MicroSD), router transaction logs and DHCP leases, mobile companion application artifacts, and vendor cloud API access logs.
Out of Scope: Identification of real-world human actors, legal attribution of motive or intent, and investigation of any real third-party devices, cloud accounts, or proprietary networks.

1.3 Competing Alternative Hypotheses

  • H1 (Device Compromise): The camera's local software, runtime memory, or firmware was altered by an unauthorized party via local serial interface, network vulnerability, or unauthorized executable, bypassing cloud authorization.
  • H2 (Cloud Account Misuse): An unauthorized party compromised the owner's cloud credentials or hijacked an authentication token (reflected by session=S-0002) to dispatch valid management commands through the cloud API.
  • H3 (Benign Malfunction): A software fault, cloud synchronization retry race condition, or firmware defect altered the setting and initiated clip uploads without malicious intervention.
  • H4 (Authorized User Action): An authorized user with legitimate access (e.g. secondary family member or keyholder) altered the setting and forgot or failed to inform the primary owner.

2.1 Order of Volatility (RFC 3227)

Evidence acquisition strictly follows the volatility order defined in RFC 3227:

Order ID Evidence Location Volatility Risk if Collection Delayed
1 E1 Camera RAM & Active Sockets High Instantly lost upon power interruption; overwritten during ongoing execution.
2 E2 Router State & DHCP/NAT Tables Medium-High Overwritten by circular logging or state expiration under high traffic.
3 E5 Companion App Local Cache Medium Subject to automatic cloud synchronization overwrites upon app launch.
4 E6 Cloud API & Storage Telemetry Medium Subject to vendor retention windows (often 7–30 days) and account modification.
5 E4 MicroSD Video & Offline Cache Low Non-volatile, but can be overwritten by circular ring-buffer recording if left powered on.
6 E3 Camera SPI NOR Flash (Firmware) Lowest Highly persistent. Low risk if extracted with appropriate hardware tools.

6. Limitations

  1. Synthetic Data Constraints: All logs, network flows, and session IDs analyzed are synthetic. Real IoT embedded systems exhibit asynchronous multi-threaded kernel noise, binary logging formats, and non-linear clock drift that require specialized reverse engineering.
  2. Hardware Hypothesis Untested (H1 Open): Because live physical hardware was not acquired or probed, hypothesis H1 (Device Compromise) remains untested rather than disproven. The absence of compromise indicators in high-level logs does not prove local security.
  3. Cryptographic Scope: A matching SHA-256 hash confirms that a file has remained unaltered since the moment it was first hashed; it cannot prove that the file was authentic or uncompromised when initially generated on the device.
  4. Heuristic Rule Boundaries: The four rules in evidence_tool.py represent demonstration detection patterns, not a complete intrusion detection engine. Attackers can masquerade processes under allowed names (e.g., camerad).
  5. Plain JSON Log Security: Storing the audit trail in a local plaintext JSON file is vulnerable to manipulation if the analyst workstation is compromised. In production forensics, logs must be written to append-only write-once media or a remote SIEM.

7. Qualified Conclusion

Based strictly on the synthetic artifacts evaluated in the Section 4 Evidence Matrix:

  • Hypotheses Cannot Be Definitive: The available evidence cannot definitively isolate one single hypothesis among the four possibilities.
  • Cloud-Side Leaning (Low Confidence): The technical facts confirm that the motion alert setting was altered through a command issued via the cloud API (CMD_RECEIVED matching CONFIG_CHANGE at 02:10:07) following a newly authenticated session (S-0002 at 23:55:02). This sequence is slightly more consistent with cloud-side account interaction (H2: Cloud Account Misuse or H4: Authorized User Action) than with an isolated on-device hardware compromise (H1).
  • Device Compromise (H1) and Malfunction (H3) Not Excluded: Because volatile RAM and SPI flash were not extracted, H1 is untested, not excluded. Similarly, backend cloud automation or synchronization failures (H3) could account for the setting change without human user interaction.
  • The 4-Minute Gap is Not Proof of Causation: The 4-minute 4-second interval between the setting change (02:10) and the first video upload (02:14) represents a temporal correlation only. It does not establish that the setting change caused the uploads or that the same actor initiated both events.
  • Attribution Boundaries: The findings do not name any individual, establish motive, or determine criminal intent. Forensic evidence demonstrates what state transitions occurred on the system; attribution of authorship requires corroborating external records.
